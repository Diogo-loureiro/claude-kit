# Code Quality, Testing & Security for a Fully Agentic Workflow (AI writes ~100% of code, no manual code review)

Research date: 2026-10-31. Labels used: **[EVIDENCE]** = study, measurement, or vendor data (vendor bias noted); **[VENDOR-GUIDANCE]** = official tool or vendor docs; **[OPINION]** = practitioner or blog opinion; **[INFERENCE]** = my synthesis. Most figures come from search snippets and secondary coverage unless the note says the primary page was fetched. Fetched primary pages: martinfowler.com (Böckeler) and code.claude.com best-practices.

## 1. Do Clean Code, SOLID, and conventions still matter when the agent writes everything? Does codebase quality affect agent success and token cost?

### Takeaway
Yes, but the reason has changed. Code health now matters mainly as an input to the agent: it drives agent defect rates and token consumption. It is no longer mainly about human readability. The strongest evidence is CodeScene's 2026 peer-reviewed study (vendor-authored). The industry trend (OpenAI, Böckeler/Thoughtworks, Anthropic) is to enforce structure mechanically with linters, structural tests, and hooks rather than through prose style guides.

### Cited Findings
- **[EVIDENCE, Jan 2026, vendor-authored peer-reviewed]** Borg & Tornhill (CodeScene), "Code for Machines, Not Just Humans: Quantifying AI-Friendliness with Code Health Metrics." AI coding assistants raise defect risk by at least 30% when applied to unhealthy code, and real-world risk is likely higher in legacy code. The press release calls AI "a technical debt multiplier" in unhealthy code. — [PR Newswire release 2026-01-28](https://tools.prnewswire.com/en-us/live/20823/release/20260128EN71904)
- **[EVIDENCE, CodeScene blog numbers relayed by a secondary blog, June 2026]** Agents used up to about 50% more tokens on unhealthy code: C++ +43.8%, Java +45.1%, Python +35.4% (Qwen3-Coder-30b). In Java, iterative refactoring produced about 120% more output tokens when Code Health fell below 8. Median coverage of agent-generated tests was much lower in unhealthy code: Python 46.6% (CH ≥ 9.8) vs 19.4% (CH < 6); C++ 35.2% vs 3.2%. A Code Health of at least 9.4 was cited as needed to keep AI-induced bugs in check. The study covered about 25k files in C++, Java, and Python. — [Daniel Vaughan blog summarizing CodeScene, 2026-06-06](https://codex.danielvaughan.com/2026/06/06/ai-ready-code-health-codescene-research-codex-cli-agent-performance-quality-gates/). Caveat: these numbers are second-hand. The risk bands (6.0–9.3) are the blog author's synthesis.
- **[EVIDENCE, vendor case study]** loveholidays saw code health decline in early agentic use of Claude. After adding Code Health gates (an MCP server), it went from 0% to 50% agent-assisted code in 5 months while keeping quality. — [PR Newswire 2026-01-28](https://tools.prnewswire.com/en-us/live/20823/release/20260128EN71904)
- **[EVIDENCE, Oct 2025, arXiv 2510.03178]** "When Names Disappear": name-only obfuscation severely degrades LLM intent-level tasks such as summarization. Execution-prediction tasks also drop consistently. Identifiers are a major channel LLMs use to understand code, so naming conventions still matter. — [arXiv 2510.03178](https://arxiv.org/html/2510.03178v1)
- **[EVIDENCE, Feb 2025, vendor dataset]** GitClear "AI Copilot Code Quality 2025" analyzed 211M changed lines from 2020 to 2024. Duplicated code blocks rose about 8x in 2024. Churn rose from 3.3% (2021) to 5.7% (2024), per secondary coverage. A 7.1% figure for 2025 appears to be a projection, not a measurement. GitClear sells measurement tools. — [LeadDev](https://leaddev.com/technical-direction/how-ai-generated-code-accelerates-technical-debt); [Rob Bowley 2025-02-17](https://blog.robbowley.net/2025/02/17/gitclears-latest-report-indicates-genai-is-having-a-negative-impact-on-code-quality/)
- **[EVIDENCE/PRACTICE, OpenAI, Feb 2026, secondary coverage; primary returned 403]** OpenAI's "Harness engineering" experiment: about 1M lines written by Codex over roughly 5 months with no human-written code. The team enforced a strict layered architecture per domain (Types → Config → Repo → Service → Runtime → UI). Dependencies were "enforced mechanically" by custom linters and structural tests, which Codex itself generated. Lint error messages doubled as remediation instructions. AGENTS.md was kept to about 100 lines as a map pointing to deeper docs. — [ignorance.ai summary](https://www.ignorance.ai/p/the-emerging-harness-engineering); [datasciencedojo](https://datasciencedojo.com/blog/harness-engineering/). The primary URL is openai.com/index/harness-engineering/ and returned 403, so verify details there.
- **[VENDOR-GUIDANCE/OPINION, Thoughtworks, 2026-04-02, fetched]** Böckeler, "Harness engineering for coding agent users." Its model is guides (feedforward: AGENTS.md, style guides) plus sensors (feedback: tests, linters, review agents), and you need both. Computational sensors (linters, type checkers, ArchUnit-style structural tests) "reliably catch duplication, complexity, coverage gaps, architectural drift, and style violations." LLM review can partly catch semantic duplication and over-engineering but is too costly for every commit. "Harnessability": strong typing, clear module boundaries, and opinionated frameworks make more controls available. — [martinfowler.com](https://martinfowler.com/articles/harness-engineering.html)
- **[VENDOR-GUIDANCE, Anthropic, current docs, fetched]** Claude Code best practices split instructions into non-deterministic ones (CLAUDE.md, skills: "Claude is allowed to decide a guideline doesn't apply") and deterministic ones (hooks, deny rules). "If you keep adding emphasis to a CLAUDE.md line and Claude still misses it, that's a sign the line belongs in a hook. The reverse holds too: if you have hooks for things that are only preferences, delete them." Keep CLAUDE.md under 200 lines, holding only what Claude can't infer from code: exact test, typecheck, and lint commands. Models infer conventions from the code itself. — [code.claude.com/docs/en/best-practices](https://code.claude.com/docs/en/best-practices)

### Inferences
- **[INFERENCE]** Keep the parts of Clean Code and SOLID that are mechanically checkable or that directly reduce the context an agent needs: descriptive names, small cohesive modules, explicit boundaries and dependency direction, no duplication, low cyclomatic complexity, and strong types. Drop the ceremonial parts (deep abstraction hierarchies, interfaces for everything). They add files and indirection the agent must read, and Anthropic warns that over-eager reviewers push toward "extra abstraction layers."
- **[INFERENCE]** The codebase itself is the strongest prompt. Agents copy existing patterns, so an early, consistent, healthy codebase compounds and a messy one compounds debt (the GitClear and CodeScene findings point the same way).
- **[INFERENCE]** Prefer enforcing conventions over describing them. Each convention should be either inferable from the code or a lint rule; a CLAUDE.md line is a last resort.

### Gaps
- I could not access the original CodeScene paper's exact break-rate curves and thresholds; the numbers come via press and a blog. There is no independent replication of the token-cost effect.
- The OpenAI primary post could not be fetched (403), so its details come from secondary summaries.
- I found no controlled study isolating SOLID specifically (as opposed to "code health" overall) against agent success.

## 2. File and function size limits: still worth having?

### Takeaway
Yes, as a soft limit enforced by a linter, not as dogma. File reads dominate agent token spend (>70% per SWE-Pruner Pro), Claude Code's Read tool truncates at 2,000 lines by default, and practitioners report edit degradation from about 700–1,000 lines. No benchmark proves a specific number. About 300–500 lines per file (warn) and about 50–80 lines per function is a reasonable heuristic.

### Cited Findings
- **[EVIDENCE, Jul 2026, arXiv 2607.18213]** SWE-Pruner Pro: on SWE-Bench Verified, file-reading commands account for over 70% of tokens consumed by Mini-SWE-Agent with Claude Sonnet 4.5, with a similar pattern for GLM-4.6. Context pruning saves up to 39% of tokens without quality loss. — [HF papers 2607.18213](https://huggingface.co/papers/2607.18213.md). The "76%" figure in the brief was **not** confirmed; I found ">70%".
- **[EVIDENCE, Jan 2026, arXiv 2601.16746]** SWE-Pruner (goal-guided line-level pruning of file-read output) reached a 64% success rate on SWE-Bench Verified with 31% fewer tokens and up to 26% fewer interaction rounds. Whole-file reads are largely waste. — [arXiv 2601.16746](https://arxiv.org/html/2601.16746v1)
- **[VENDOR-BEHAVIOUR, community-reported]** Claude Code's Read tool returns the first 2,000 lines by default, and lines over 2,000 characters are truncated. The agent must page with offset/limit. One GitHub issue reports that line-number formatting makes Read cost about 1.7x the raw tokens, and that 63% of a 5,000-line file was silently truncated. — [GitHub issue #20223](https://github.com/anthropics/claude-code/issues/20223); [DEV walkthrough](https://dev.to/_94be737e156beb4d74df2/claude-code-tools-deep-dive-5-read-2ba6)
- **[OPINION/anecdotal]** Cursor users report agents becoming "much less effective" above about 700 LOC per file and "a nightmare" above 1,200. Windsurf files of 800–1,000 lines needed 2–6 reverts. A Gemini Build-mode refactor of a 1,600-line file came back at 400–500 lines, losing functionality. One vendor-adjacent guide puts the edit/apply risk zone at 500–1,000 lines and says rewrites of files over 1,000 lines can run out of output tokens. — [Cursor forum](https://forum.cursor.com/t/max-file-length-for-ai-edits-refactor-to-multiple-files/2989); [fast.io](https://fast.io/resources/cursor-file-size-limit/); [Google AI forum](https://discuss.ai.google.dev/t/build-mode-seems-to-be-behaving-incorrectly/119814)
- **[OPINION]** Set a `max-lines` lint rule about 20% above the largest file you deliberately keep. It is "a forcing function, not a precise number," and cohesion matters more than size. — [DEV: The five-thousand-line file must die](https://dev.to/tacoda/the-five-thousand-line-file-die)
- **[EVIDENCE, indirect]** CodeScene's Code Health metric penalizes large methods, deep nesting, and "brain methods," and lower health correlates with more agent tokens and defects (see section 1). — [CodeScene via Vaughan](https://codex.danielvaughan.com/2026/06/06/ai-ready-code-health-codescene-research-codex-cli-agent-performance-quality-gates/)

### Inferences
- **[INFERENCE]** Small files help agents in three ways. (a) The agent reads only the relevant unit, cutting the dominant token cost. (b) Exact-match string-replace edits (Claude Code Edit requires unique `old_string`) are more reliable in shorter files. (c) The file is never truncated by the 2,000-line Read window.
- **[INFERENCE]** Recommended soft limits: file warns at 400 and errors at 600–800 lines (exclude generated code and test fixtures); function warns at about 60–80 lines; cyclomatic or cognitive complexity about 10–15. Tools: ESLint `max-lines`, `max-lines-per-function`, `complexity`; Biome `noExcessiveCognitiveComplexity`; Ruff `C901` (mccabe) and `PLR0915` (too-many-statements). Don't split files just to meet a number when that breaks cohesion. Excessive fragmentation also costs tokens through more reads and indirection.

### Gaps
- I found no controlled benchmark that measures agent edit accuracy against file length. All thresholds are heuristics.
- I could not confirm the current official Read default in Claude Code docs (2,000 lines comes from tool-description copies and issues).

## 3. Linters, formatters, and type checkers as deterministic guardrails

### Takeaway
Deterministic computational sensors are the cheapest, most reliable guardrail. Run them on every edit or stop via hooks and again in CI. Make them quiet on success and fail fast. Write custom lint messages that tell the agent how to fix the problem. Enforce architecture with dependency-cruiser or import-linter. Protect the linter configs from the agent.

### Cited Findings
- **[VENDOR-GUIDANCE, Anthropic, fetched]** Recommended wiring: a `PostToolUse` hook on Edit/Write runs the formatter. A `Stop` hook runs typecheck and sends errors to stderr; exit code 2 blocks the turn from ending "until the typecheck passes or the block limit is reached" (8 consecutive blocks; configurable via `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`). A `PreToolUse` hook exits 2 to block protected paths such as `migrations/`. Use `command` hooks (not prompt or agent hooks) for real enforcement. Add `onFailure: "block"` for security hooks such as secret scanning so a crashed scanner doesn't pass silently. "Keep the enforced set small… If you ever find yourself at forty of them, most are probably preferences." — [code.claude.com best practices](https://code.claude.com/docs/en/best-practices)
- **[VENDOR-GUIDANCE, Böckeler, fetched]** Sensor output should be optimized for LLM consumption, such as custom linter messages with fix instructions. Keep quality left: linters, fast tests, and a basic review agent before commit; mutation testing and broader architecture review post-integration; dead code, coverage quality, and dependency scanning as continuous drift monitoring. — [martinfowler.com](https://martinfowler.com/articles/harness-engineering.html)
- **[PRACTICE, OpenAI via secondary]** Custom linters and structural tests enforce layer dependencies, with error messages that double as remediation instructions. — [ignorance.ai](https://www.ignorance.ai/p/the-emerging-harness-engineering)
- **[OPINION/PRACTICE, HumanLayer]** "Context-efficient backpressure": swallow all test, build, and lint output on success and print a single ✓. Dump the stashed output only on a nonzero exit. Fail fast (`pytest -x`, `jest --bail`, `go test -failfast`) so the agent fixes one failure at a time. The motivation is staying inside a roughly 75k-token "smart zone." HumanLayer's token figures are illustrative, not benchmarked. — [HumanLayer blog](https://www.humanlayer.dev/blog/context-efficient-backpressure); [understandingdata.com](https://understandingdata.com/posts/context-efficient-backpressure/)
- **[OPINION, practitioner]** Agents may edit linter configs or add disable comments instead of fixing code. Protect the configs (`.eslintrc`, `biome.json`, `pyproject [tool.ruff]`, `tsconfig`) with a PreToolUse hook. Use a fast typecheck (for example `tsgo`) in the Stop hook. — [understandingdata.com hooks quality gates](https://understandingdata.com/posts/claude-code-hooks-quality-gates/)

### Concrete tool choices (from tool documentation; I did not re-fetch these docs this session)
- **TS/Node:** Biome (format + lint, one Rust binary, fast; [biomejs.dev](https://biomejs.dev/)) **or** ESLint (flat config, richer plugin ecosystem, needed for custom architectural rules and `typescript-eslint` type-aware rules) + Prettier. Type checking: `tsc --noEmit` with `"strict": true`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`. Architecture: [dependency-cruiser](https://github.com/sverweij/dependency-cruiser) (forbidden-dependency rules, cycles, orphans; each rule has a `comment` field usable as a fix hint) or ESLint `no-restricted-imports` / `eslint-plugin-boundaries`. Dead code and unused deps: [knip](https://knip.dev/).
- **Python:** [Ruff](https://docs.astral.sh/ruff/) (lint + format, replaces flake8/isort/black). Typecheck with mypy `--strict` or pyright/basedpyright (Astral's `ty` is newer; check maturity). Architecture: [import-linter](https://import-linter.readthedocs.io/) contracts (layers, forbidden, independence). Validate money and DTO types with Pydantic or `Decimal`, never `float`.
- **Quiet flags:** `tsc --noEmit --pretty false`; `eslint --quiet` (errors only); `biome check --reporter=summary` or `--diagnostic-level=error`; `ruff check --quiet --output-format=concise`; `mypy --no-error-summary` or `--hide-error-context`; `pytest -q -x --no-header -p no:warnings`; `vitest run --reporter=dot --bail=1`.

### Inferences
- **[INFERENCE]** Lean wiring: PostToolUse runs format plus lint autofix on the changed file only (fast, silent). The Stop hook runs typecheck, lint (errors only), affected tests, and the architecture check, prints output only on failure, and exits 2 on failure. CI reruns everything from scratch. Format-on-edit avoids spending tokens on style discussions.
- **[INFERENCE]** Every recurring agent mistake becomes either a lint rule with a fix message or a structural test. Only rules with zero exceptions become hooks.

### Gaps
- I found no measured study of token savings from quiet or fail-fast output; the evidence is practitioner-level.
- I did not verify current Biome vs ESLint feature parity for custom architectural rules (Biome plugin support via GritQL is evolving).

## 4. Testing strategy for agent-written code without human review

### Takeaway
Tests are the main specification and the main sensor, but AI-written tests are often weak: they encode the actual (possibly buggy) behaviour and assert little. Agents excel when given correct tests (TDFlow: 88.8–94.3% with human-written tests). So the human-approved part should be the acceptance criteria and test intent, not the code. Use property-based tests for invariants (especially money), and mutation testing to measure test strength. Coverage alone is not enough.

### Cited Findings
- **[EVIDENCE, EACL 2026]** TDFlow (Han et al., CMU): a test-driven agentic workflow with sub-agents (propose, debug, revise, optionally generate tests) and constrained tools. Given human-written tests it reached 88.8% on SWE-Bench Lite and 94.3% on SWE-Bench Verified. Only 7 of 800 manually reviewed runs showed "test hacking." The authors conclude that the main remaining bottleneck is writing accurate reproduction tests, not resolving given tests. — [ACL Anthology author page](https://aclanthology.org/people/kevin-han)
- **[EVIDENCE, Dec 2024, arXiv 2412.14137]** LLM test generators (CoverAgent, CoverUp) run against real buggy Python code can produce tests that accept faulty behaviour, and their design (discarding failing tests) can reject bug-revealing tests. — [arXiv 2412.14137](https://arxiv.org/html/2412.14137v1)
- **[EVIDENCE, Oct 2024, arXiv 2410.21136]** LLM-generated oracles tend to capture actual rather than expected behaviour. When code is buggy, generated tests are likely wrong (24 Java repos). — [arXiv 2410.21136](https://arxiv.org/html/2410.21136v1)
- **[EVIDENCE, 2025]** Recent studies identify oracle weakness (shallow assertions with low mutation score), not lack of coverage, as the main limitation of LLM tests. Coverage and mutation score diverge persistently (GEM, CIbSE 2025). MUTGEN (arXiv 2506.02954) argues that line and branch coverage are "weak indicators" of fault-detection capability. — [GEM, SBC](https://sol.sbc.org.br/index.php/cibse/article/view/42441); [arXiv 2506.02954](https://arxiv.org/pdf/2506.02954v6)
- **[EVIDENCE, Oct 2025, NeurIPS 2025 workshop, Anthropic/Northeastern]** An agentic property-based testing agent (Claude Opus 4.1 writing Hypothesis tests) ran on 100 popular Python packages. 56% of reported bugs were valid, and 86% of the top-21 ranked. Bugs found included numerical precision and serialization issues; patches were merged into NumPy and others. Agents can write good property tests. — [arXiv 2510.09907](https://arxiv.org/html/2510.09907v1)
- **[EVIDENCE, small study, review summary only]** LLM-generated PBT on 16 HumanEval problems: recommends a hybrid with PBT for broad coverage and example-based tests for specific boundaries. — [themoonlight review](https://www.themoonlight.io/review/understanding-the-characteristics-of-llm-generated-property-based-tests-in-exploring-edge-cases)
- **[OPINION, Böckeler 2026-04-02, fetched]** The "behaviour harness" is still unsolved. Relying on AI-generated tests is "not good enough yet." The approved-fixtures (snapshot/approval testing) pattern helps. Mutation testing is a "resurging" underused sensor and belongs in the post-integration pipeline because of its cost. — [martinfowler.com](https://martinfowler.com/articles/harness-engineering.html)
- **[VENDOR-GUIDANCE, Anthropic, fetched]** Write a SPEC.md first, then build in a fresh session. Prompt pattern: "write a failing test that reproduces it, then fix it." Ask for evidence (the command and its output), not "all tests pass." Review against the spec with a read-only reviewer subagent ("check every requirement is implemented and the listed edge cases have tests… skip style"). — [code.claude.com best practices](https://code.claude.com/docs/en/best-practices)
- **[OPINION, practitioner]** "Green doesn't mean correct": LLM tests pass "because they were written to agree with your code." — [Medium](https://medium.com/@lcarvalho.dev/green-doesnt-mean-correct-aff359a1d45e)

### Inferences (recommended lean strategy)
- **[INFERENCE] Shape:** Use the testing trophy. Most value comes from integration tests at module or API boundaries (real DB via testcontainers or SQLite, HTTP via supertest or httpx), plus unit tests for pure domain logic, a few e2e smoke tests (Playwright) on critical journeys, and static checks as the base. Agents refactor freely, so tests tied to implementation details break or get "fixed" tautologically.
- **[INFERENCE] Human gate on intent, not code:** The human approves acceptance criteria and examples (Given/When/Then or a table of inputs and expected outputs), ideally as a test file stub the agent may not edit. Enforce that with a PreToolUse hook blocking edits to `tests/acceptance/**` or approved snapshot fixtures. Then the agent implements until green (TDFlow pattern).
- **[INFERENCE] Money and finance:** Integer cents or `Decimal` only. Write property tests (fast-check for TS, Hypothesis for Python) for invariants: sums conserve (splits add up to the total), rounding stays within one cent, conversions round-trip, balance = Σ transactions, idempotent imports, and no negative balance where forbidden. Add example tests for known edge dates (month end, leap year, DST, timezone).
- **[INFERENCE] Mutation testing:** Use Stryker (`@stryker-mutator`, `--incremental`, mutate only changed files) for TS, and mutmut or cosmic-ray for Python. Run on domain and core modules only, nightly or on PRs touching them; a full run on every commit is too slow. Use the mutation score threshold (for example ≥ 60–70% on core) as the "are the AI tests real?" gate. Coverage gate: a modest diff-coverage floor (for example 80% on changed lines) rather than a global vanity target.
- **[INFERENCE] Contract tests:** Only where there are separately deployed consumers and providers or external APIs (Pact, or schema validation with zod or Pydantic at boundaries). Skip for a monolith.

### Gaps
- I did not verify primary details of TDD-Bench in this pass.
- I found no study quantifying mutation score of Claude- or Codex-written test suites in real projects (2026).
- No empirical comparison of the testing pyramid vs the testing trophy specifically for agent workflows.

## 5. Replacing manual review: AI review, SAST, secrets, dependencies, supply chain

### Takeaway
AI code is still frequently insecure: Veracode 2026 found a 56% security pass rate, flat over time and not fixed by bigger models. Package hallucination is about 20% in research settings. Without human review, use layered deterministic gates (SAST, secret scanning, SCA, lockfile and dependency-allowlist checks) plus an independent AI reviewer in a fresh context, aimed at correctness against the spec. LLM reviewers have meaningful false-positive and false-negative rates, so treat them as a sensor, not an oracle.

### Cited Findings
- **[EVIDENCE, Veracode, 2026-07-28]** 2026 GenAI Code Security Report: over 100 models across four snapshots. Average security pass rate is about 56%, vs 55% in the first (2025) report, so about 44% of tasks produce code with a known vulnerability. Model size has essentially no effect (large 53%, medium 51%, small 51%). Coding-specific models are no more secure. Best models on the Summer 2026 leaderboard: GPT-5.5 at 68%; GPT-5.3-Codex and Claude Opus 4.8 at 62%. By language: Python 63% (best), Java 30% (worst). — [Veracode press release](https://www.veracode.com/news/llms-are-getting-smarter-but-not-safer-veracode-2026-genai-code-security-report-finds-ai-generated-code-security-has-stalled-at-56%25-pass-rate/); [SD Times](https://sdtimes.com/agentic-security/veracode-finds-ai-generated-code-security-has-barely-improved-since-last-year/); [infographic](https://www.veracode.com/wp-content/uploads/2026-GenAI-Report-Infographic.pdf). Note: other secondary sources cite "45% of tasks" (the 2025 report and the Spring 2026 snapshot), which is consistent in magnitude.
- **[EVIDENCE, USENIX Security 2025, Spracklen et al.]** Package hallucination across 16 models and 576k code samples: 19.7% of package references were hallucinated (205,474 unique fake names). Commercial models averaged about 5.2% and open-source models about 21.7%. 43% of hallucinated names recurred on every rerun, making them predictable for attackers ("slopsquatting"). 8.7% of hallucinated Python names exist as npm packages. — [the-decoder](https://the-decoder.com/slopsquatting-one-in-five-ai-code-snippets-contains-fake-libraries/); [Socket](https://socket.dev/blog/slopsquatting-how-ai-hallucinations-are-fueling-a-new-class-of-supply-chain-attacks); [Endor Labs](https://www.endorlabs.com/learn/hallucinated-packages-how-ai-invents-dependencies-attackers-exploit). The figures are secondary; the original is arXiv 2406.10279.
- **[VENDOR-GUIDANCE, OWASP]** OWASP Top 10 for Agentic Applications (ASI01–ASI10), published 2025-12-09 by the OWASP GenAI Security Project. It covers agent risks (tool misuse, privilege, memory poisoning and others) relevant to coding agents' own permissions. I found no dedicated OWASP standard for "AI-generated code" itself. Secondary guidance: AI code bound for production must pass the standard gates (SAST, SCA, secure review), and agents should get least privilege, with human approval for high-impact actions. — [aigl.blog index of OWASP Agentic Top 10](https://www.aigl.blog/owasp-top-10-for-agentic-applications-2026.md); [Endor Labs agentic dev security](https://www.endorlabs.com/learn/agentic-development-security-how-to-secure-code-your-agents-write)
- **[VENDOR-GUIDANCE, Anthropic, fetched]** `/code-review` "reviews the diff in a fresh subagent that never saw your conversation. It isn't swayed by the reasoning that produced the code." Use a read-only reviewer subagent (`tools: Read, Grep, Glob`). Warning: "A reviewer that's asked to find problems will always find *something*. If you fix every finding, you end up with extra abstraction layers and tests for cases that can't happen." Subagents cost tokens and "by default it's the same model… you get a fresh pair of eyes, not a smarter answer." — [code.claude.com best practices](https://code.claude.com/docs/en/best-practices). Claude Code also ships a `/security-review` command (observed in this environment's skill list).
- **[EVIDENCE, 2026, mixed quality]** LLM code reviewers show over-correction bias: they often wrongly reject correct code (arXiv, Feb 2026). A Waterloo MSc thesis (Sept 2026, open-weight models on Kafka history) found substantial false positives and false negatives and concluded that assistant-style use fits better than autonomous defect-finding. An informal benchmark of 4 commercial reviewers on 146 PRs found false-positive rates from 2.3% to 15% (high-severity tier). — [arXiv 2603.00539](https://arxiv.org/html/2603.00539v1); [UWaterloo](https://uwaterloo.ca/computer-science/events/masters-thesis-presentation-se-how-well-do-automated-code-reviewing-tools-detect-bugs); [DEV benchmark](https://dev.to/_vjk/best-ai-code-reviewer-in-2026-we-ran-4-in-parallel-for-3-weeks-146-prs-679-findings-1c0f)
- **[VENDOR-GUIDANCE, Anthropic]** Use deny rules, PreToolUse hooks, and the sandbox for "never" rules (for example never read `.env`). Auto-mode classifier judgments can be wrong. — [code.claude.com best practices](https://code.claude.com/docs/en/best-practices)

### Concrete tool choices (tool docs, not re-fetched)
- **SAST:** [Semgrep CE](https://semgrep.dev/) (fast, pre-commit or CI, `p/owasp-top-ten`, `p/typescript`, `p/python` rulesets, custom rules in YAML) and/or [CodeQL](https://codeql.github.com/) via GitHub code scanning (deeper dataflow, slower, free on public repos and with GHAS). Python extra: Bandit (or Ruff's `S` rules, which port Bandit).
- **Secrets:** [gitleaks](https://github.com/gitleaks/gitleaks) as a pre-commit hook and in CI, plus GitHub push protection.
- **Dependencies/SCA:** [OSV-Scanner](https://github.com/google/osv-scanner) (lockfile-based, multi-ecosystem), `npm audit --audit-level=high` or `pip-audit`, and Dependabot or [Renovate](https://docs.renovatebot.com/) for updates. Renovate's `minimumReleaseAge` delays very new versions, which helps against freshly published malicious packages.
- **Anti-slopsquatting:** Fail CI if a new dependency appears in the manifest diff without an explicit approval label. Verify packages exist, are older than N days, and are popular (Socket.dev or a simple registry check script). Always commit lockfiles, use `npm ci` or `uv sync --frozen`, and consider `npm config set ignore-scripts true`.
- **Branch protection:** Require CI status checks, linear history, no force-push, and code-scanning alerts blocking merges. The agent works on branches and PRs; merge is automated only when all gates are green.

### Inferences
- **[INFERENCE]** Because model choice moves the security pass rate only from about 50% to 68%, security has to come from the pipeline, not the model. Deterministic SAST and SCA are cheap and catch the common CWE classes Veracode measures (injection, XSS, crypto misuse, log injection).
- **[INFERENCE]** Run the AI reviewer once per PR, not per edit. Run it in a fresh context against SPEC.md and the acceptance criteria, focused on correctness and security, with "skip style." Triage only high-confidence findings to avoid over-engineering loops. Use `/security-review` for diffs touching auth, money, input parsing, or file and network I/O.
- **[INFERENCE]** The human's remaining review effort goes to spec and acceptance criteria approval, new-dependency approval, and changes to the harness itself (lint config, hooks, CI, permissions), which the agent should not be able to modify unreviewed.

### Gaps
- I did not fetch the full Veracode report for CWE-level breakdowns (the brief summary lists XSS and log injection as historically worst; not re-verified here).
- I found no rigorous public benchmark of Claude Code `/code-review` precision and recall.
- OWASP primary pages were not fetched; dates come from secondary sources.

## 6. Lean recommended quality-gate stack and order (local hooks to CI) with token-efficiency tips

### Takeaway
Use a three-tier pipeline of cheap deterministic checks first and expensive inferential ones last: (1) agent hooks per edit and per stop; (2) git pre-commit and pre-push; (3) CI on PR, with nightly or periodic heavier checks. All output is silent on success and fail-fast on failure. The human approves specs and acceptance tests, new dependencies, and harness changes, not code.

### Cited Findings
- **[VENDOR-GUIDANCE]** Order recommended by Böckeler (2026-04-02): pre-commit gets linters, fast tests, and a basic review agent; post-integration gets mutation testing and broader review; continuous monitoring covers dead code, coverage quality, and dependencies; runtime gets SLO and log feedback. — [martinfowler.com](https://martinfowler.com/articles/harness-engineering.html)
- **[VENDOR-GUIDANCE]** Anthropic: PostToolUse formatter, Stop-hook typecheck (exit 2), PreToolUse block on protected paths, `onFailure: "block"` for secret scanning, a small enforced set, CLAUDE.md under 200 lines with the exact verify commands, and a read-only reviewer subagent or `/code-review` in a fresh context. Haiku is suggested for simple subagents to cut cost. — [code.claude.com best practices](https://code.claude.com/docs/en/best-practices)
- **[OPINION]** Silent success and fail-fast to stay inside the "smart zone" of context. — [HumanLayer](https://www.humanlayer.dev/blog/context-efficient-backpressure)
- **[EVIDENCE]** Healthy code means about 35–45% fewer agent tokens (CodeScene, vendor), and file reads are more than 70% of tokens (SWE-Pruner Pro). Code structure is a token-cost lever. — see sections 1 and 2.

### Inferences: proposed lean stack (stack-agnostic, with TS and Python examples)
**Tier 0, before coding (human, minutes):** SPEC.md with acceptance criteria and examples. The agent writes acceptance tests, the human approves them, and they are then locked by a PreToolUse hook. New-dependency policy.

**Tier 1, agent hooks (seconds, every edit or turn):**
1. PreToolUse: block edits to `.env*`, lint and type config, CI workflows, `migrations/`, and locked acceptance tests or snapshots. Deny rules for reading secrets.
2. PostToolUse (Edit/Write, changed file only): `biome check --write <file>` or `prettier --write && eslint --fix --quiet`; for Python `ruff format <file> && ruff check --fix --quiet <file>`.
3. Stop hook (exit 2 on failure, stderr only on failure): `tsc --noEmit` (or `tsgo`) / `mypy --strict` or `pyright`; architecture check (`depcruise src --output-type err` / `lint-imports`); affected tests (`vitest related --run --bail=1` / `pytest -q -x --lf` or `pytest-testmon`).

**Tier 2, git hooks (pre-commit via lefthook, husky, or pre-commit.com):** gitleaks (staged files), plus the Tier 1 checks for non-agent commits. Pre-push: full unit and integration suite (quiet).

**Tier 3, CI on PR (required status checks, branch protection):** clean install from the lockfile (`npm ci` / `uv sync --frozen`); format check, lint, typecheck, and architecture; full tests with a diff-coverage floor; Semgrep (+ CodeQL if on GitHub); gitleaks; OSV-Scanner or `npm audit` / `pip-audit`; a new-dependency gate; Playwright smoke e2e; an AI reviewer (`/code-review` or a headless Claude review against SPEC.md, plus `/security-review` on sensitive paths). Auto-merge only when everything is green.

**Tier 4, nightly or weekly:** Stryker or mutmut incremental on core and domain modules with a mutation-score threshold; knip or vulture for dead code; Renovate updates (with a minimum release age); code-health and duplication trend (jscpd, or CodeScene if budget allows); full CodeQL.

**Token-efficiency tips [INFERENCE unless cited]:**
- Wrap every check in a `run_quiet` script (stash output, print ✓ or the first N failure lines, keep the exit code). Use fail-fast flags.
- Run per-file or affected-only checks in the agent loop; full suites in CI.
- Keep files small and cohesive (soft limit about 400–500 lines), the biggest lever on read tokens.
- Keep CLAUDE.md/AGENTS.md short (Anthropic: under 200 lines; OpenAI: about 100-line map) and put procedures in skills, which load on demand.
- Lint messages carry the fix ("Import from `domain/` only via `domain/index.ts`; move X to Y"), so the agent fixes the issue in one turn instead of investigating.
- One AI review per PR, in a fresh context, with "skip style." Use a cheaper model for mechanical subagents.
- Each recurring failure becomes a new lint rule or structural test (ratchet). Prune hooks that encode mere preferences.

### Gaps
- No end-to-end empirical comparison of gate stacks for agentic workflows exists. The stack above is a synthesis of vendor guidance, practitioner patterns, and indirect evidence.
- Token cost of the CI-tier AI review per PR was not measured in sources found.
